# 第一阶段技术栈拆解：从 Node + SQLite 演进到视觉/听觉/触觉同步采集

文档日期：2026-05-25  
背景：之前系统主要用 Node + SQLite 直接采集触觉数据；现在要加入视频、音频、全身触觉、回放和后续数据平台能力。  

## 1. 先给结论

你现在不需要一下子上很多复杂技术。

第一阶段可以继续保留：

> Node + SQLite 作为采集控制、元数据管理和本地回放系统的核心。

真正需要新增的是：

1. **视频采集**：用 FFmpeg 录第一人称视频。
2. **音频采集**：用 FFmpeg 或系统音频 API 录麦克风。
3. **统一时间戳**：让视频、音频、手套、鞋垫、全身衣能对齐。
4. **文件化存储**：视频、音频、触觉原始数据不要都塞进 SQLite。
5. **同步回放界面**：能同时看视频、触觉热力图、事件标签。

第一阶段推荐：

| 模块 | 现在建议 |
|---|---|
| 主程序 | 继续用 Node |
| 本地数据库 | 继续用 SQLite |
| 视频/音频录制 | Node 调 FFmpeg |
| 触觉数据 | 继续 Node 采集，但写成文件 + SQLite 索引 |
| 回放界面 | 如果你已有前端，就继续用 Web/React；没有就先做简单本地页面 |
| 数据导出 | 先 CSV/JSONL，后续再 Parquet/MCAP |
| ROS 2 | 第一阶段可不做，只预留 |
| Kafka/K8s/数据湖 | 第一阶段完全不做 |

## 2. 你原来的 Node + SQLite 是干什么的

你原来的系统大概承担了三件事：

| 功能 | Node 做什么 | SQLite 做什么 |
|---|---|---|
| 设备采集 | 连接触觉硬件，读取压力数据 | 记录采集任务、设备、数据 |
| 本地管理 | 控制开始/停止、保存文件 | 保存历史记录 |
| 简单回放/查看 | 读取数据展示 | 查询历史数据 |

这个基础可以继续用。

问题是：当你加入视频、音频、全身衣后，**SQLite 不适合直接存所有原始大数据**。

## 3. 为什么不能什么都放 SQLite

SQLite 适合存：

1. session 信息。
2. 设备信息。
3. 文件路径。
4. 时间范围。
5. 标签。
6. 质量指标。
7. 小规模索引。

SQLite 不适合大量直接存：

1. 视频帧。
2. 音频波形。
3. 高频全身触觉矩阵。
4. 大量二进制数组。

所以第一阶段应该改成：

> SQLite 存“索引和元数据”，原始数据存成文件。

## 4. 第一阶段最小架构

```text
Node 采集主程序
  ├─ 控制触觉手套采集
  ├─ 控制触觉鞋垫采集
  ├─ 控制全身衣采集
  ├─ 调用 FFmpeg 录视频/音频
  ├─ 生成统一 session_id
  ├─ 写入统一时间戳
  ├─ 保存原始数据文件
  └─ 写 SQLite 元数据

本地 session 文件夹
  ├─ metadata.json
  ├─ video.mp4
  ├─ audio.wav
  ├─ glove.csv / glove.jsonl
  ├─ insole.csv / insole.jsonl
  ├─ fullbody.csv / fullbody.jsonl
  ├─ events.jsonl
  └─ session.sqlite

回放界面
  ├─ 播放视频
  ├─ 按时间读取触觉数据
  ├─ 展示手套热力图
  ├─ 展示鞋垫热力图
  ├─ 展示全身衣接触区域
  └─ 展示事件标签
```

## 5. 每个技术到底是干什么的

### 5.1 Node

Node 在第一阶段继续做主控。

它负责：

1. 开始采集。
2. 停止采集。
3. 连接设备。
4. 调用 FFmpeg。
5. 创建 session 文件夹。
6. 写 SQLite。
7. 提供本地 API 给前端回放。

你不用因为要做视频/音频就立刻换掉 Node。

### 5.2 SQLite

SQLite 继续保留，但角色要调整。

它不要当“大数据仓库”，而是当：

> 本地采集任务索引数据库。

建议 SQLite 表：

| 表 | 存什么 |
|---|---|
| `sessions` | 每次采集的 id、开始时间、结束时间、任务名称 |
| `devices` | 手套、鞋垫、全身衣、相机、麦克风 |
| `session_files` | video/audio/tactile 文件路径 |
| `events` | 接触、滑移、过压、步态等事件 |
| `quality_metrics` | 丢帧率、同步误差、断连次数 |

### 5.3 FFmpeg

FFmpeg 是用来录视频和音频的。

你可以让 Node 启动一个 FFmpeg 进程：

```text
Node start session
  ↓
启动 FFmpeg 录相机和麦克风
  ↓
同时开始触觉数据采集
  ↓
停止时关闭 FFmpeg
```

FFmpeg 输出：

1. `ego_video.mp4`
2. `audio.wav` 或视频里直接带音轨

第一阶段用 FFmpeg 比自己写视频采集模块更稳。

### 5.4 时间戳

时间戳是第一阶段最重要的技术点。

如果没有统一时间戳，视频和触觉就只是两堆数据，不能证明“视觉 + 触觉同步”的价值。

每条触觉数据至少要有：

```json
{
  "timestamp_ms": 1234567890,
  "device_id": "glove_left",
  "frame_index": 1024,
  "values": [...]
}
```

视频也要记录：

1. 视频开始时间。
2. 视频帧率。
3. 每一帧对应的大概时间。

第一阶段可以先用：

> 同一台电脑的系统时间 + 单调递增时间戳。

后面再考虑 PTP、硬件触发、ROS 时间。

### 5.5 CSV / JSONL

这是最容易开始的数据格式。

CSV 适合：

1. 鞋垫压力。
2. 手套每帧压力。
3. 简单曲线分析。

JSONL 适合：

1. 每帧数据结构不完全一样。
2. 事件标签。
3. 多区域全身衣数据。

第一阶段你可以先用：

| 数据 | 推荐格式 |
|---|---|
| 手套 | CSV 或 JSONL |
| 鞋垫 | CSV |
| 全身衣 | JSONL |
| 事件标签 | JSONL |
| 元数据 | JSON + SQLite |

### 5.6 Parquet

Parquet 是后续更适合 AI/数据分析的格式。

它解决的问题是：

1. 数据量大时 CSV 太慢。
2. 客户的数据科学团队想用 Python、DuckDB、Spark 快速读取。
3. 后续要做平台检索、筛选、导出训练集。

但第一阶段你不一定马上要写 Parquet。

推荐路线：

> 先 CSV/JSONL 跑通，再加一个导出 Parquet 的功能。

### 5.7 MCAP

MCAP 是机器人多传感器日志格式。

它适合：

1. 机器人客户。
2. ROS 生态。
3. 多传感器时间序列回放。
4. 以后对接机器人状态、IMU、关节数据。

第一阶段可以不强制做 MCAP。

建议：

> 先把数据结构设计得能导出 MCAP，后面再加 MCAP exporter。

### 5.8 ROS 2

ROS 2 是机器人系统常用中间件。

它适合：

1. 机器人皮肤。
2. 机器人关节状态。
3. 机器人相机。
4. 实时控制和日志记录。

但你现在如果只是做人穿戴采集 Demo，ROS 2 不是 P0。

建议：

| 阶段 | 是否需要 ROS 2 |
|---|---|
| 第一阶段人穿戴 Demo | 不强制 |
| 机器人客户 PoC | 需要 |
| 机器人穿戴触觉皮肤 | 需要 |
| 和客户机器人系统集成 | 基本需要 |

### 5.9 React / Web 回放界面

回放界面很重要，因为客户要“看懂”。

它要做：

1. 播放第一人称视频。
2. 同步显示手套压力。
3. 同步显示鞋垫压力。
4. 同步显示全身衣接触区域。
5. 展示事件标签。
6. 支持拖动时间轴。

如果你现在已有 Node 前端，就继续用。

如果没有，第一阶段可以做最简单的网页：

```text
左边：视频
右边：手套热力图 / 鞋垫热力图 / 全身衣区域图
底部：时间轴 + 事件标签
```

### 5.10 Python

Python 第一阶段不是主系统必须，但很适合做：

1. 数据分析。
2. 数据清洗。
3. CSV 转 Parquet。
4. 生成图表。
5. 做简单模型验证。

如果你们主系统是 Node，不需要硬切到 Python。

推荐：

> Node 做采集主程序，Python 做离线分析和导出工具。

## 6. 第一阶段技术优先级

### P0 必须做

| 技术 | 为什么必须 |
|---|---|
| Node 采集主控 | 复用现有基础 |
| SQLite 元数据 | 管理 session 和文件 |
| FFmpeg 视频/音频录制 | 加入视觉/听觉采集 |
| 统一时间戳 | 多模态同步的核心 |
| 文件化原始数据 | 避免 SQLite 存大数据 |
| 回放界面 | 客户必须看懂价值 |
| CSV/JSONL 导出 | 先让数据能被读取 |

### P1 建议做

| 技术 | 什么时候做 |
|---|---|
| Parquet 导出 | 数据量变大，或客户要分析/训练 |
| 数据质量报告 | 开始做客户 PoC 前 |
| 简单事件标注 | 需要证明抓取/滑移/接触时 |
| Python 分析脚本 | 需要做对比实验时 |
| 外部相机同步 | Demo 需要第三视角展示时 |

### P2 以后再做

| 技术 | 为什么以后再做 |
|---|---|
| MCAP | 机器人/ROS 客户来了再上 |
| ROS 2 Node | 机器人穿戴版或机器人状态接入时 |
| MinIO/S3 | 数据要上传到服务器时 |
| PostgreSQL | 多人/多客户平台时 |
| Kafka/NATS | 需要实时流处理时 |
| Kubernetes | 企业级部署和扩展时 |
| Iceberg/Delta Lake | 大规模数据湖时 |

## 7. 你现在应该怎么改现有系统

### 第一步：保留 Node + SQLite

不要推倒重来。

你只需要把 SQLite 的定位改成：

> 保存元数据和索引，不保存所有大体积原始数据。

### 第二步：定义 session 文件夹

每次采集生成一个文件夹：

```text
session_20260525_001/
  metadata.json
  session.sqlite
  video/
    ego.mp4
  audio/
    mic.wav
  tactile/
    glove_left.csv
    glove_right.csv
    insole_left.csv
    insole_right.csv
    fullbody.jsonl
  labels/
    events.jsonl
```

### 第三步：Node 启动 FFmpeg

Node 控制：

1. 启动视频录制。
2. 启动触觉采集。
3. 写入统一开始时间。
4. 停止时关闭所有采集。
5. 写入 metadata。

### 第四步：所有触觉数据加时间戳

每一帧触觉数据都要有：

1. `session_id`
2. `device_id`
3. `timestamp_ms`
4. `frame_index`
5. `values`

### 第五步：做同步回放

第一阶段回放器比平台更重要。

最小回放器只要做到：

1. 拖动视频时间。
2. 根据当前视频时间查对应触觉帧。
3. 显示手套/鞋垫/全身衣热力图。
4. 显示事件标签。

## 8. 第一阶段最小可执行版本

如果要最小化，我建议做这个：

| 组件 | 实现 |
|---|---|
| 采集主程序 | Node |
| 数据库 | SQLite |
| 视频 | FFmpeg 输出 MP4 |
| 音频 | FFmpeg 输出 WAV 或视频内音轨 |
| 触觉手套 | CSV/JSONL |
| 触觉鞋垫 | CSV |
| 全身衣 Lite | JSONL |
| 元数据 | metadata.json + SQLite |
| 回放 | Node 本地服务 + Web 页面 |
| 导出 | 打包 session 文件夹 |

这已经够支撑第一阶段 Demo。

## 9. 不同技术的关系

```text
Node
  是主控，负责把所有东西串起来

SQLite
  是目录本，记录有哪些 session、文件在哪里、标签是什么

FFmpeg
  是录像机，负责视频和音频

CSV/JSONL
  是第一阶段触觉原始数据文件

Parquet
  是后续给数据分析和训练更高效的格式

MCAP
  是后续给机器人/ROS 客户的多传感器日志格式

ROS 2
  是后续接机器人系统的接口

React/Web
  是给客户看的同步回放界面

Python
  是后续做分析、转换、模型验证的工具
```

## 10. 最重要的产品判断

第一阶段你不要追求“技术栈先进”，要追求：

> 数据采得下来、对得上、看得懂、导得出。

判断标准：

1. 能不能同时录视频、音频、手套、鞋垫、全身衣。
2. 能不能用同一个时间轴回放。
3. 能不能看到触觉比视觉多提供了什么信息。
4. 能不能导出给客户或算法同事分析。
5. 能不能发现这条数据质量好不好。

如果这 5 件事做到了，第一阶段技术栈就是对的。
