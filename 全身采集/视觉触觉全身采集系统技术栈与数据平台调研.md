# 视觉 + 触觉全身采集系统技术栈与数据平台调研

文档日期：2026-05-25  
公司方向：纤维织物触觉传感器、触觉鞋垫、触觉全身衣、触觉手套、机器人触觉皮肤  
调研问题：完整系统需要什么技术栈？后续做数据平台需要哪些技术？
使用 Skill：`product-strategy` + `metrics-dashboard`  
说明：当前技能库没有专门的“技术栈调研/系统架构选型”skill；`update-tech-doc` 只适用于代码修改后的 ARCHITECTURE.md 维护，不适合本次从零调研。因此本次用 `product-strategy` 约束阶段路线与取舍，用 `metrics-dashboard` 补齐数据平台指标体系。

## 1. 核心结论

你们的完整系统不应该一开始就做成“大数据平台”。合理路线是：

> 第一阶段先做“可同步采集、可回放、可导出”的采集系统；第二阶段做“可管理、可标注、可筛选、可训练”的数据平台；第三阶段再做“数据闭环 + 模型训练 + 客户协作”的平台化产品。

推荐技术路线：

| 阶段 | 目标 | 技术重点 |
|---|---|---|
| MVP | 证明视觉 + 全身触觉同步采集有价值 | 设备驱动、时间同步、本地记录、MCAP/Parquet、回放界面 |
| V1 数据平台 | 管理和使用采集数据 | 对象存储、元数据数据库、标注、检索、任务管理、权限 |
| V2 训练平台 | 支持机器人/世界模型训练 | 数据集版本、特征提取、LeRobot/ROS/Gym 接口、MLflow、批处理 |
| V3 企业平台 | 支持客户规模化采集 | 多设备管理、远程上传、质量监控、自动清洗、API、私有部署 |

第一阶段最重要的技术决策只有 5 个：

1. 所有数据必须有统一时间戳。
2. 原始数据必须可完整记录。
3. 回放界面必须能同步展示视频、手套、鞋垫、全身衣。
4. 数据格式必须能被机器人/AI 团队读取。
5. 数据质量必须能被评估，比如丢帧、延迟、传感器断连、同步误差。

## 2. 产品战略约束下的技术取舍

这一节按 `product-strategy` skill 梳理：技术栈不是越完整越好，而是服务当前阶段的产品战略。

### 2.1 长期愿景

长期愿景：

> 做物理世界 AI 的视觉 + 全身触觉同步数据基础设施，让人和机器人都能采集真实世界中的接触、压力、滑移、重心、碰撞和安全交互数据。

### 2.2 第一目标客户

| 客户 | 他们真正要的 | 技术系统必须支持 |
|---|---|---|
| 人形机器人公司 | 人类示教 + 机器人执行数据对齐 | 人体采集、机器人状态、触觉皮肤、ROS/MCAP 导出 |
| 世界模型/机器人基础模型团队 | 可训练的多模态物理交互数据 | 视频、触觉、音频、动作、标签、数据质量评分 |
| 具身智能实验室 | 可复现实验和可扩展数据格式 | 标定、同步、回放、数据集版本、Python/ROS SDK |

### 2.3 技术取舍

| 决策 | 选择 | 为什么 |
|---|---|---|
| 先做本地采集还是云平台 | 先本地采集 | MVP 先证明数据价值，云平台不是第一风险。 |
| 先做完整数据湖还是文件化 session | 先 session 文件结构 | 更快交付，也方便客户拿走数据。 |
| 先做大规模训练系统还是导出接口 | 先导出接口 | 客户已有训练栈，你们先成为高质量数据入口。 |
| 先做全量标注系统还是事件标注 | 先事件标注 | 触觉价值首先体现在接触、滑移、过压、步态事件。 |
| 先做所有传感器抽象还是固定套件 | 先固定套件 | 第一阶段聚焦相机 + 手套 + 鞋垫 + 全身衣 Lite。 |

### 2.4 当前不做事项

为了避免技术平台过早膨胀，MVP 阶段暂不做：

1. 多租户企业 SaaS。
2. 大规模数据湖 Iceberg/Delta。
3. Kubernetes 集群。
4. Kafka 实时流处理平台。
5. 完整自动标注系统。
6. 强化学习训练平台。
7. 客户自定义硬件协议市场。
8. 医疗合规级数据平台。

这些不是永远不做，而是等到数据采集闭环和客户 PoC 成立后再做。

## 3. 完整系统分层

建议把系统分成 9 层：

| 层级 | 作用 | 典型技术 |
|---|---|---|
| 1. 传感器硬件层 | 采集视觉、触觉、IMU、音频、机器人状态 | 相机、麦克风阵列、触觉矩阵、IMU、机器人关节状态 |
| 2. 设备驱动层 | 把硬件数据变成统一数据流 | C/C++ SDK、Python SDK、ROS 2 Node、USB/BLE/Wi-Fi/CAN/EtherCAT |
| 3. 时间同步层 | 保证多模态数据能对齐 | PTP/NTP、硬件触发、统一 monotonic timestamp、frame_id |
| 4. 边缘采集层 | 本地实时采集、缓存、压缩、断点续传 | C++/Rust/Python、ROS 2、GStreamer、FFmpeg、SQLite |
| 5. 数据记录层 | 把一次采集保存成 episode/session | MCAP、ROS bag2、MP4、Parquet、Zarr/HDF5 |
| 6. 数据上传层 | 从采集端上传到数据平台 | S3 API、分片上传、断点续传、MQTT/NATS/Kafka |
| 7. 数据平台层 | 管理 session、设备、用户、任务、标签、版本 | PostgreSQL、对象存储、DuckDB/ClickHouse、FastAPI、React |
| 8. 标注与回放层 | 查看、筛选、标注、导出训练集 | Web 播放器、CVAT/Label Studio、Foxglove、Plotly/WebGL |
| 9. 模型训练接口层 | 输出给世界模型/机器人训练 | PyTorch、LeRobot、ROS 2、Gymnasium、MLflow、DVC |

## 4. MVP 技术栈建议

第一阶段不要追求“平台”，而是做一个可靠的采集闭环：

> 采集 → 同步 → 记录 → 回放 → 导出 → 给客户看。

### 3.1 MVP 架构

```text
相机 / 麦克风 / 手套 / 鞋垫 / 全身衣
        ↓
设备驱动与采集程序
        ↓
统一时间戳 + session_id + frame_id
        ↓
本地记录：MCAP + MP4 + Parquet
        ↓
本地/网页回放器
        ↓
导出样例数据集
```

### 3.2 MVP 推荐选型

| 模块 | 推荐技术 | 原因 |
|---|---|---|
| 采集程序 | Python + C++ 混合 | Python 开发快，C++ 处理高频驱动和性能敏感部分。 |
| 机器人/多传感器通信 | ROS 2 | 机器人客户熟悉，支持 topic、bag、QoS、DDS。 |
| 视频采集 | GStreamer / FFmpeg / OpenCV | 生态成熟，方便录制、压缩、转码、预览。 |
| 触觉数据记录 | MCAP + Parquet | MCAP 适合多通道时间序列日志；Parquet 适合后续分析。 |
| 视频文件 | MP4/H.264 或 H.265 | 通用、体积可控、浏览器容易播放。 |
| 原始矩阵数据 | Parquet 或 Zarr | Parquet 适合表格型时序；Zarr 适合大规模 N 维数组。 |
| 本地元数据 | SQLite | MVP 简单可靠，记录 session、设备、标签、路径。 |
| 回放界面 | React + WebGL/Canvas + FastAPI | 可快速做视频 + 触觉热力图同步展示。 |
| 数据分析 | Python + NumPy/Pandas/Polars + DuckDB | 快速处理和查询本地数据。 |

### 3.3 MVP 不建议先用

| 暂不建议 | 原因 |
|---|---|
| Kafka 大集群 | 第一阶段数据量和实时消费链路还不需要。 |
| Kubernetes | 会增加部署和运维复杂度。 |
| Spark/Flink | 只有大规模批处理/流处理时才需要。 |
| 完整数据湖 Iceberg/Delta | MVP 阶段先用对象存储 + Parquet 足够。 |
| 自研复杂标注系统 | 先做轻量标签，或接 CVAT/Label Studio。 |
| 复杂用户权限体系 | 第一阶段只需要内部账号和客户演示权限。 |

## 5. 数据格式建议

你们的数据比较特殊：既有视频，又有高频触觉矩阵，还有事件标签、人体区域、机器人状态。建议采用“分层存储”，不要试图把所有东西塞进一个文件。

### 4.1 推荐 session 目录结构

```text
session_20260525_001/
  metadata.json
  timeline.parquet
  video/
    ego_camera.mp4
    external_camera.mp4
  tactile/
    glove_left.parquet
    glove_right.parquet
    insole_left.parquet
    insole_right.parquet
    fullbody.zarr
  audio/
    mic.wav
  ros/
    session.mcap
  labels/
    events.jsonl
    annotations.json
  exports/
    lerobot/
    pytorch/
```

### 4.2 各格式适合什么

| 格式 | 适合数据 | 是否推荐 |
|---|---|---|
| MCAP | 多通道、带时间戳、机器人/传感器日志 | 强烈推荐 |
| ROS bag2 | ROS 生态录制回放 | 推荐，但建议优先支持 MCAP storage |
| Parquet | 触觉时序表、事件表、指标表、元数据分析 | 强烈推荐 |
| Zarr | 大规模触觉矩阵、全身热力图、N 维数组 | 推荐 |
| HDF5 | 科研场景常见 N 维数组 | 可兼容，不建议作为唯一主格式 |
| MP4 | 视频 | 推荐 |
| WAV/FLAC | 音频 | 推荐 |
| JSON/JSONL | 标签、事件、配置、轻量元数据 | 推荐 |

### 4.3 为什么推荐 MCAP

MCAP 是面向多模态日志数据的开源容器格式，支持多个带时间戳的 channel，并能保存 Protobuf、ROS、JSON Schema 等消息。它非常适合机器人、自动驾驶、硬件采集和物理 AI 的“录制-回放-分析”工作流。

你们可以用它保存：

1. 相机帧时间戳。
2. 触觉矩阵消息。
3. IMU。
4. 机器人关节状态。
5. 事件标签。
6. 设备状态。

### 4.4 为什么推荐 Parquet / Arrow

Parquet 适合分析型列式存储，Arrow 是跨语言的内存列式格式。对你们来说：

1. 客户的数据科学团队容易用 Python、DuckDB、Spark、Polars 读取。
2. 可以按 session、device、timestamp、region 快速筛选。
3. 后续做数据平台、数据湖、训练集导出会更顺。

### 4.5 为什么推荐 Zarr

全身触觉衣可能产生连续的大矩阵/多维数组。Zarr 是 chunked、compressed 的 N 维数组格式，适合大规模数组分块读写和云对象存储。

适合保存：

1. 全身衣压力矩阵。
2. 多区域热力图。
3. 长时间采集的高频触觉序列。
4. 模型训练用的 tensor 数据。

## 6. 数据平台需要哪些技术

后续数据平台本质上是一个“机器人/人体多模态数据管理平台”，不是普通后台管理系统。

### 5.1 数据平台核心能力

| 能力 | 说明 |
|---|---|
| Session 管理 | 每次采集任务的时间、设备、人员、场景、数据路径。 |
| 设备管理 | 手套、鞋垫、全身衣、相机、机器人皮肤的序列号、固件、标定版本。 |
| 数据上传 | 支持本地采集端断点续传、校验、失败重试。 |
| 数据质量检查 | 丢帧、延迟、同步误差、传感器断连、异常值、噪声。 |
| 多模态回放 | 视频、触觉热力图、音频、IMU、机器人状态同步播放。 |
| 标注 | 接触开始/结束、滑移、过压、抓取成功、步态阶段、人机接触安全。 |
| 检索 | 按任务、设备、标签、客户、时间、质量评分筛选数据。 |
| 数据集构建 | 从 session 里挑选片段，生成训练集版本。 |
| 导出 | 导出为 LeRobot、PyTorch Dataset、ROS bag/MCAP、Parquet。 |
| 权限与审计 | 客户数据隔离、操作日志、下载权限、隐私合规。 |

### 5.2 后端技术栈

| 模块 | 推荐技术 | 说明 |
|---|---|---|
| API 服务 | FastAPI / Go / Node.js | Python 便于和数据处理打通；Go 适合高并发和边缘服务。 |
| 元数据数据库 | PostgreSQL | 管理 session、设备、用户、任务、标签、标定版本。 |
| 对象存储 | S3 / MinIO | 存视频、MCAP、Parquet、Zarr、模型和导出文件。 |
| 本地分析查询 | DuckDB | 直接查 Parquet，非常适合早期数据平台和离线分析。 |
| 大规模分析 | ClickHouse / Trino / Spark | 数据量大以后再引入。 |
| 任务队列 | Celery/RQ + Redis，或 NATS | 用于转码、质检、导出、特征提取。 |
| 搜索 | PostgreSQL + 索引，后续 Elasticsearch/OpenSearch | 早期先别上复杂搜索集群。 |
| 缓存 | Redis | 缓存回放索引、任务状态、临时结果。 |
| 认证权限 | Keycloak / Auth0 / 自研轻量 RBAC | 企业客户后续需要租户隔离。 |

### 5.3 前端技术栈

| 模块 | 推荐技术 | 说明 |
|---|---|---|
| Web 应用 | React / Next.js | 做数据管理、回放、标注、客户演示。 |
| 热力图展示 | Canvas / WebGL / deck.gl | 手套、鞋垫、全身衣热力图需要高效渲染。 |
| 曲线图 | ECharts / Plotly | 压力曲线、重心轨迹、传感器状态。 |
| 视频同步 | HTML5 video + 时间轴控制 | 以视频时间为主轴同步触觉和事件。 |
| 3D 展示 | Three.js | 后续展示人体/机器人模型上的触觉分布。 |
| 标注交互 | 自研轻量组件 + 可集成 CVAT/Label Studio | 触觉事件标注和普通视觉框选不完全一样。 |

### 5.4 标注系统

| 方案 | 适用情况 | 建议 |
|---|---|---|
| 自研轻量事件标注 | 接触、滑移、过压、步态阶段 | MVP 首选 |
| CVAT | 图像/视频框选、分割、关键点 | 适合视觉标注，不够覆盖触觉矩阵 |
| Label Studio | 多类型数据标注，灵活配置 | 适合快速原型和多模态标签 |
| 自研多模态标注平台 | 视频 + 触觉 + 音频 + 机器人状态同步标注 | V1/V2 再做 |

建议第一阶段自研最小标注能力：

1. 在时间轴上打点：接触开始、接触结束。
2. 标片段：滑移、抓稳、步态周期、危险接触。
3. 标任务结果：成功/失败。
4. 标压力事件：峰值、过压、左右失衡。

## 7. 采集端技术栈

### 6.1 采集端必须解决的问题

| 问题 | 为什么重要 |
|---|---|
| 时间同步 | 视觉和触觉错 100ms，滑移/抓取判断就可能失真。 |
| 丢帧检测 | 数据不能只采，还要知道哪里坏了。 |
| 设备状态 | 电量、连接、固件、采样率、温度、校准状态。 |
| 本地缓存 | 采集现场网络不稳定，必须本地可靠保存。 |
| 标定版本 | 同一套数据必须知道用了哪个标定参数。 |
| 隐私处理 | 第一人称视频和人体数据敏感。 |

### 6.2 采集端推荐架构

```text
Device Drivers
  ├─ Camera Driver
  ├─ Tactile Glove Driver
  ├─ Insole Driver
  ├─ Full-body Suit Driver
  ├─ Audio Driver
  └─ Optional Robot State Driver

Edge Recorder
  ├─ Time Sync Manager
  ├─ Data Quality Monitor
  ├─ MCAP Writer
  ├─ Video Encoder
  ├─ Local Metadata DB
  └─ Upload Agent
```

### 6.3 采样率建议

| 数据 | 建议频率 | 说明 |
|---|---:|---|
| 第一人称视频 | 30 fps 起步，60 fps 更好 | 抓取和滑移最好 60 fps。 |
| 外部视频 | 30 fps | 用于演示和第三视角对齐。 |
| 音频 | 16kHz/48kHz | 语音指令和环境声音。 |
| 手套触觉 | 50-200Hz | 抓取和滑移需要较高频率。 |
| 鞋垫触觉 | 50-200Hz | 步态和重心足够。 |
| 全身衣触觉 | 20-100Hz | 接触安全和压力区域可先低一些。 |
| IMU | 100-200Hz | 姿态和动作同步。 |
| 机器人关节状态 | 50-250Hz | 看机器人控制系统要求。 |

## 8. 机器人与 AI 生态接口

### 7.1 ROS 2

ROS 2 是机器人客户最熟悉的中间件之一。它支持 topic、bag、QoS、DDS，适合多节点、多传感器、机器人状态数据交换。

建议你们至少提供：

1. `tactile_glove_node`
2. `tactile_insole_node`
3. `tactile_suit_node`
4. `tactile_skin_node`
5. `session_recorder_node`
6. ROS 2 message definitions
7. MCAP/rosbag2 录制示例

### 7.2 LeRobot / Hugging Face 机器人学习生态

LeRobot 正在成为机器人学习数据、训练和评测的一个重要开源生态。它的数据集使用标准化结构，并支持机器人策略训练、数据集工具和 Hugging Face Hub。

你们后续可以提供：

1. `export_to_lerobot.py`
2. 触觉 observation schema。
3. 视频 + 触觉 + action 的 episode 格式。
4. 用触觉数据训练抓取/滑移预测的 baseline。

### 7.3 仿真与训练

| 方向 | 推荐技术 |
|---|---|
| 机器人仿真 | NVIDIA Isaac Sim / Isaac Lab、MuJoCo、Gazebo |
| 强化学习接口 | Gymnasium |
| 模型训练 | PyTorch |
| 实验追踪 | MLflow |
| 数据版本 | DVC / lakeFS / 对象存储版本 |
| 数据集发布 | Hugging Face Datasets / 私有对象存储 |

## 9. 数据质量体系

你们的数据平台如果要卖给世界模型/机器人公司，必须有数据质量指标。否则客户拿到数据也不知道能不能训练。

### 8.1 质量指标

| 指标 | 说明 |
|---|---|
| 同步误差 | 视频帧、触觉帧、音频、IMU 的时间偏差。 |
| 丢帧率 | 每个设备实际采样帧数 / 理论采样帧数。 |
| 延迟 | 从传感器采样到记录/显示的延迟。 |
| 抖动 | 采样间隔是否稳定。 |
| 断连次数 | 采集中设备掉线次数。 |
| 压力饱和率 | 传感器是否大量达到最大值。 |
| 零漂/噪声 | 无接触状态下的基线波动。 |
| 标定版本 | 采集时使用的标定文件。 |
| 数据完整性 | 文件 checksum、大小、时间范围是否匹配。 |

### 8.2 质量评分

建议给每条 session 一个 `quality_score`：

```text
quality_score =
  同步质量 * 0.3
  + 丢帧质量 * 0.25
  + 传感器稳定性 * 0.2
  + 标定有效性 * 0.15
  + 标签完整性 * 0.1
```

这会成为数据平台非常重要的能力：客户不是只要“更多数据”，而是要“能训练的高质量数据”。

## 10. 数据平台指标看板

这一节按 `metrics-dashboard` skill 梳理：数据平台不能只显示“采了多少数据”，必须追踪哪些数据真正可用、可训练、可交付。

### 10.1 North Star Metric

| 指标 | 定义 | 数据来源 | 目标 |
|---|---|---|---|
| 可训练高质量采集时长 | `质量合格 session 中，视频 + 触觉 + 标签完整的有效分钟数` | session 元数据、质量检测、标签系统 | MVP 阶段先达到 300-500 分钟可演示/可训练数据 |

这个指标比“采集总时长”更好，因为它会逼团队关注同步、丢帧、标注和可训练性。

### 10.2 输入指标

| 指标 | 定义 | 数据来源 | 可视化 | 告警阈值 |
|---|---|---|---|---|
| Session 合格率 | `quality_score >= 80 的 session 数 / 总 session 数` | 质量检测服务 | 趋势线 + 分布图 | 连续 3 天低于 80% |
| 多模态同步合格率 | `同步误差低于阈值的通道数 / 总通道数` | recorder、timestamp 日志 | 通道热力图 | 任一核心通道误差 > 100ms |
| 标签完整率 | `已标注关键事件的有效片段 / 应标注片段` | 标注系统 | 漏斗图 | 低于 70% |
| 触觉有效覆盖率 | `有效触觉传感点 / 总传感点` | 设备自检、采集数据 | 设备矩阵图 | 单设备低于 90% |
| 导出成功率 | `成功导出训练集任务 / 总导出任务` | 导出服务 | 柱状图 | 低于 95% |

### 10.3 健康指标

| 指标 | 定义 | 数据来源 | 告警阈值 |
|---|---|---|---|
| 采集端丢帧率 | 每个设备实际帧数与理论帧数差异 | recorder | 视频 > 2%，触觉 > 5% |
| 设备断连次数 | 单次 session 内设备掉线次数 | device status | 核心设备断连 > 0 |
| 压力饱和率 | 达到量程上限的传感点比例 | tactile data | 超过 5% 需要检查量程/标定 |
| 上传失败率 | 上传失败任务 / 上传任务 | upload agent | 超过 3% |
| 回放加载时间 | 打开 session 到可播放的时间 | 前端埋点 | 超过 5 秒 |
| 存储成本/小时 | 每小时合格数据的存储成本 | 对象存储 + 元数据 | 月环比异常增长 > 30% |

### 10.4 业务指标

| 指标 | 定义 | 为什么重要 |
|---|---|---|
| PoC 转化率 | 看过 Demo 后进入 PoC 的客户比例 | 判断技术演示是否打动目标客户。 |
| 客户数据复采率 | 客户是否愿意再次采集数据 | 判断数据价值是否真实存在。 |
| 每个客户有效数据时长 | 单客户产出的高质量可训练数据分钟数 | 判断能否成为数据平台而非一次性硬件项目。 |
| 数据集导出次数 | 客户或内部导出训练集次数 | 判断数据是否被真正用于模型训练。 |

### 10.5 看板布局

```text
North Star
  可训练高质量采集时长

采集质量
  Session 合格率 / 同步误差 / 丢帧率 / 断连次数

触觉质量
  有效覆盖率 / 饱和率 / 零漂噪声 / 标定版本

标注与导出
  标签完整率 / 导出成功率 / 数据集版本数

客户与业务
  PoC 转化率 / 复采率 / 客户有效数据时长
```

### 10.6 复盘节奏

| 频率 | 看什么 | 决策 |
|---|---|---|
| 每天 | 丢帧、断连、同步误差、上传失败 | 修 recorder、驱动、硬件连接问题 |
| 每周 | Session 合格率、标签完整率、有效数据时长 | 判断采集流程是否稳定 |
| 每月 | PoC 转化率、导出次数、客户复采率 | 判断产品价值是否成立 |
| 每季度 | North Star、存储成本、客户留存 | 判断是否进入平台化投入 |

## 11. 数据平台阶段路线

### 9.1 Phase 0：本地采集与演示

目标：把 Demo 做出来。

必做：

1. 多设备采集。
2. 统一时间戳。
3. 本地保存。
4. 同步回放。
5. 导出样例数据。

技术栈：

1. Python/C++。
2. ROS 2 可选但建议预留。
3. MCAP、MP4、Parquet。
4. SQLite。
5. React/FastAPI 或本地 Python UI。

### 9.2 Phase 1：内部数据平台

目标：团队能管理 100-1000 条 session。

必做：

1. 上传和数据目录管理。
2. session 搜索。
3. 质量检测。
4. 简单标注。
5. 导出训练集。

技术栈：

1. PostgreSQL。
2. S3/MinIO。
3. FastAPI。
4. React。
5. DuckDB。
6. Celery/Redis。

### 9.3 Phase 2：客户 PoC 平台

目标：客户能上传、查看、筛选、下载自己的数据。

必做：

1. 多租户。
2. 权限。
3. 标注协作。
4. 数据质量报告。
5. API。
6. 私有部署包。

技术栈：

1. PostgreSQL + 对象存储。
2. Keycloak/Auth0。
3. Docker Compose，后续 Kubernetes。
4. OpenTelemetry + Prometheus + Grafana。
5. CVAT/Label Studio 集成。

### 9.4 Phase 3：大规模训练数据平台

目标：服务世界模型/机器人基础模型团队。

必做：

1. 百万级 episode 管理。
2. 数据集版本。
3. 自动清洗。
4. 分布式转码/特征提取。
5. 训练集导出。
6. 与模型训练和仿真平台集成。

技术栈：

1. Iceberg/Delta Lake。
2. Trino/Spark/ClickHouse。
3. Kafka/NATS。
4. MLflow。
5. DVC/lakeFS。
6. Kubernetes。

## 12. 推荐产品技术路线

### 10.1 第一阶段最小技术栈

如果你们现在要开工，建议只选这些：

| 层 | 技术 |
|---|---|
| 采集 | Python + C++ |
| 机器人接口 | ROS 2 message/node 预留 |
| 视频 | FFmpeg/GStreamer + MP4 |
| 触觉记录 | Parquet + MCAP |
| 元数据 | JSON + SQLite |
| 回放 | React + FastAPI |
| 分析 | Python + DuckDB |
| 文件组织 | session 目录结构 |

第一阶段不要先纠结数据湖、Kafka、Kubernetes。你们真正要证明的是：

> 一条 session 能不能稳定采下来、对齐、回放、标注、导出，并让客户看懂触觉数据的价值。

### 10.2 第二阶段平台技术栈

| 层 | 技术 |
|---|---|
| 后端 | FastAPI / Go |
| 数据库 | PostgreSQL |
| 对象存储 | S3 / MinIO |
| 查询 | DuckDB + 后续 ClickHouse |
| 任务队列 | Celery + Redis / NATS |
| 标注 | 自研轻量标注 + Label Studio/CVAT 集成 |
| 前端 | React / Next.js |
| 权限 | Keycloak / Auth0 |
| 观测 | OpenTelemetry + Prometheus + Grafana |
| 部署 | Docker Compose → Kubernetes |

### 10.3 第三阶段 AI 数据平台技术栈

| 层 | 技术 |
|---|---|
| 数据湖 | S3/MinIO + Iceberg/Delta |

| 模型训练 | PyTorch |
| 机器人学习 | LeRobot / Gymnasium / ROS 2 |

| 数据版本 | DVC / lakeFS |

## 13. 关键技术风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 时间同步不准 | 多模态数据无法训练 | 第一阶段就做同步误差评估工具。 |
| 数据格式混乱 | 后续平台重构成本高 | 先定义 session schema 和文件组织。 |
| 视频和触觉无法顺畅回放 | 客户看不懂价值 | 回放器是 P0，不是附属功能。 |
| 全身衣数据量大 | 存储和渲染压力高 | 分块存储，低频预览，高频原始数据单独保存。 |
| 标定缺失 | 数据不可比较 | 每条 session 绑定 calibration_version。 |
| 只采不标 | 数据无法用于模型 | 至少支持事件级标签。 |
| 平台过早复杂化 | 团队被基础设施拖慢 | 按阶段引入技术，不提前上大数据栈。 |

## 14. 建议下一步

1. 先定义 `Session Schema v0.1`：session、device、timestamp、touch_map、video_frame、event_label。
2. 做一个本地 recorder：能同时录第一人称视频、手套、鞋垫、全身衣 Lite。
3. 统一输出一个 session 目录：`metadata.json + MP4 + Parquet + MCAP + labels.jsonl`。
4. 做一个同步回放器：视频、手部热力图、足底热力图、全身接触热力图。
5. 做数据质量报告：同步误差、丢帧率、断连、压力饱和。
6. 再考虑平台化上传、检索、标注和导出。
